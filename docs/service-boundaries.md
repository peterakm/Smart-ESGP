# Smart-ESGP Service Boundaries

Smart-ESGP now has two deployable server entrypoints.

## FELDA Dashboard And Certification Server

```text
server.ts
dist/server.mjs
```

Purpose:

- serve the React dashboard
- expose farmer, evidence, compliance, and certification APIs
- expose FELDA monitoring APIs for WhatsApp sessions/events
- show the farmer feedback generated by the chatbot for completed check-ins
- keep WhatsApp webhook ingestion and manual WhatsApp sends disabled by default in production
- allow auditors to review evidence and apply certification decisions
- issue and read certificate registry records
- keep local Vite development support

Commands:

```text
npm run dev
npm run start
```

Default port:

```text
3000
```

## WhatsApp Chatbot Service

```text
whatsapp-server.ts
dist/whatsapp-server.mjs
```

Purpose:

- receive Meta WhatsApp webhook callbacks
- manage farmer onboarding state
- collect GPS/photo evidence
- send chatbot replies through WhatsApp Cloud API, or dry-run locally
- store evidence and media metadata for FELDA review
- append audit events for webhook processing and evidence collection

Commands:

```text
npm run dev:whatsapp
npm run start:whatsapp
```

Default port:

```text
3100
```

Override with:

```text
WHATSAPP_PORT=3100
```

or:

```text
PORT=3100
```

## Shared State

Both entrypoints currently use:

```text
SMART_ESGP_REPOSITORY=file
SMART_ESGP_DATA_FILE=.smart-esgp-data/dev-store.json
SMART_ESGP_MEDIA_STORAGE=local-filesystem
SMART_ESGP_MEDIA_DIR=.smart-esgp-media
```

For local development this lets the WhatsApp service collect evidence while the FELDA dashboard reads and reviews it.

For production, both services should point to the same managed database and private object storage:

```text
SMART_ESGP_REPOSITORY=postgres
DATABASE_URL=postgres://...
SMART_ESGP_MEDIA_STORAGE=s3
SMART_ESGP_S3_BUCKET=smart-esgp-private-evidence
```

PostgreSQL migrations are available at:

```text
db/migrations/
```

## Route Separation

Dashboard server exposes:

```text
/health
/ready
/api/farmers
/api/evidence
/api/evidence/:evidenceId/media-url
/api/evidence/:evidenceId/media
/api/evidence/:evidenceId/review
/api/consents
/api/audit/events
/api/certificates
/api/certificates/issue
/api/certificates/verify/:verificationHash
/api/compliance/farmers/:farmerId/evaluation
/api/whatsapp/events
/api/whatsapp/farmers/:farmerId/events
/api/whatsapp/message-claims
/api/whatsapp/sessions
/api/chat
```

`/api/whatsapp/events` and `/api/whatsapp/farmers/:farmerId/events` return a sanitized monitoring projection. They include the normalized inbound summary, chatbot reply text/intent, outbound send status, and session state needed by FELDA, but they do not expose the raw Meta webhook payload, outbound message body, outbound recipient, or duplicate `reply.toPhone` recipient field. Completed check-in replies can include `reply.feedback`, which lets FELDA see the status, score, evidence-day progress, review state, risk level, and next action that the farmer received. They can also include a small `reply.evidence` summary with evidence ID, activity, verification/review status, and GPS-to-plot validation status so operators can spot outside-plot check-ins from the WhatsApp activity feed. The farmer-scoped route lets the dashboard load a selected farmer's feedback history directly instead of filtering a small global feed in the browser.

Both monitoring event routes support `?gpsReview=true`. This returns only completed WhatsApp check-ins whose GPS validation is `outside_plot`, `unknown_plot`, or `missing_location`, allowing the FELDA dashboard to load the GPS Review activity feed from the backend instead of filtering a general recent-event list in the browser.

Both monitoring event routes also support `?outboundMode=sent`, `?outboundMode=dry_run`, and `?outboundMode=failed`. The dashboard uses `?outboundMode=failed` for the failed-send operations tab so FELDA operators can inspect Meta/API delivery problems without exposing raw provider payloads, outbound message text, or recipient phone numbers.

`/api/whatsapp/message-claims` lets the dashboard show active, expired, processed, and duplicate webhook claim counts. Expired open claims indicate webhook work that can be recovered by the next Meta retry after the configured claim TTL.

The dashboard shows this feedback in two places: the global WhatsApp activity monitor and the selected farmer's WhatsApp Feedback History panel.

`/api/evidence` supports backend filtering for review operations. The dashboard uses `?review=open` for the FELDA intake queue, and operators can combine it with `locationValidationStatus=outside_plot`, `unknown_plot`, `missing_location`, or `inside_plot` for GPS triage views.

`/api/audit/events` supports dashboard-only operational filters such as `service`, `severity`, `entityType`, and exact `action`. The standalone WhatsApp service writes audit events through the shared repository but does not expose the audit read API.

The FELDA dashboard consumes filtered audit reads for warning/error operational alerts while keeping the full audit stream available below them.

In production, the dashboard does not mount:

```text
/api/whatsapp/webhook
/api/whatsapp/messages
```

For controlled demos or compatibility tests only, the production dashboard can temporarily opt in:

```text
SMART_ESGP_DASHBOARD_ENABLE_WHATSAPP_WEBHOOK=true
SMART_ESGP_DASHBOARD_ENABLE_WHATSAPP_MANUAL_SEND=true
```

Local `npm run dev` keeps those demo routes enabled by default.

WhatsApp service exposes:

```text
/health
/ready
/api/whatsapp/webhook
/api/whatsapp/messages
```

`POST /api/whatsapp/webhook` is the public Meta-facing ingestion endpoint. Its response is limited to processing counts and outbound mode totals; it does not return generated replies or full send results.

The same webhook accepts Meta delivery status callbacks. Statuses are normalized into `whatsapp.delivery.status` audit events; failed statuses use `severity=error` so the private FELDA dashboard can show them in operational alerts without exposing raw Meta payloads.

Raw Meta message payload persistence is controlled by `SMART_ESGP_RETAIN_WHATSAPP_RAW_PAYLOADS`. Production should keep this `false` so the WhatsApp service stores normalized message fields, evidence, session state, and audit events without retaining the original provider message object.

`POST /api/whatsapp/messages` is auditor-protected and returns sanitized send status only. It does not echo the farmer recipient phone number or outbound message body in the API response.
The route accepts only international WhatsApp recipient numbers with 8 to 15 digits after optional formatting characters.

The standalone WhatsApp service intentionally does not expose the FELDA dashboard, farmer list, certification evaluation, audit read API, WhatsApp monitoring routes, or message-claim monitoring route.

## Production Deployment Shape

```text
Meta WhatsApp Cloud API
  -> public HTTPS URL for WhatsApp service
  -> shared database/object storage
  -> private FELDA dashboard/certification server
  -> FELDA SSO and auditor workflow
```

Recommended next production steps:

- keep `WHATSAPP_APP_SECRET` configured for webhook signatures
- deploy the dashboard behind FELDA SSO or equivalent role-based identity controls
- expose only the standalone WhatsApp service through the Meta webhook URL and controlled outbound API
- run the compose rehearsal or equivalent infrastructure checks before release

`npm run smoke:whatsapp-service` verifies that the standalone WhatsApp service accepts the configured Meta webhook verification challenge, rejects the wrong verification token, rejects unsigned and invalidly signed webhook POSTs when `WHATSAPP_APP_SECRET` is configured, and still accepts the correctly signed Meta payload.

## Health And Readiness

Both services expose:

```text
GET /health
GET /ready
```

`/health` answers whether the process is alive.

`/ready` answers whether the service is safe to receive production traffic. It returns `503` when required production configuration is missing.
It also checks the active repository connection so a service can be removed from rotation if the shared store is unreachable.

Both services handle `SIGTERM` and `SIGINT` by closing the HTTP listener and repository connection before exiting.

Both services apply the shared security baseline:

- remove Express fingerprinting headers
- set basic browser hardening headers
- keep browser CORS same-origin by default
- allow only exact origins configured through `SMART_ESGP_ALLOWED_ORIGINS`

Both services use the shared API error boundary so malformed JSON and unexpected async failures return JSON errors instead of leaking framework error pages or unhandled promise failures.

Both services enforce bounded JSON request bodies before route handling. Configure a shared default with `SMART_ESGP_JSON_BODY_LIMIT`, or override per service with `SMART_ESGP_DASHBOARD_JSON_BODY_LIMIT` and `SMART_ESGP_WHATSAPP_JSON_BODY_LIMIT`. Values should look like `256kb`, `1mb`, or a byte count such as `50000`. Oversized bodies return a controlled JSON `413` response.

Dashboard list/read APIs also clamp `?limit=` through `SMART_ESGP_API_LIST_LIMIT_MAX`, defaulting to `100` with an absolute ceiling of `1000`. Responses include the applied `limit` so operators can see when a request was capped.

Both services attach an `x-request-id` to every response. Safe incoming request IDs are preserved; otherwise the service generates one. Set `SMART_ESGP_ACCESS_LOGS=true` to emit JSON access logs with the same request ID.

Production readiness is enabled when either of these is set:

```text
NODE_ENV=production
SMART_ESGP_DEPLOYMENT_ENV=production
```

Dashboard production readiness requires:

- `DATABASE_URL` when `SMART_ESGP_REPOSITORY=postgres`, or explicit `SMART_ESGP_DATA_FILE` when using file mode
- valid `SMART_ESGP_FILE_*_LIMIT` retention settings when using file mode
- authentication enabled through `SMART_ESGP_REQUIRE_AUTH=true` or configured role tokens
- auditor-level token or future FELDA identity integration

WhatsApp service production readiness requires:

- `DATABASE_URL` when `SMART_ESGP_REPOSITORY=postgres`, or explicit `SMART_ESGP_DATA_FILE` when using file mode
- valid `SMART_ESGP_FILE_*_LIMIT` retention settings when using file mode
- `SMART_ESGP_MEDIA_STORAGE=s3` with `SMART_ESGP_S3_BUCKET`, or explicit `SMART_ESGP_MEDIA_DIR` when using local media mode
- non-placeholder `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` when using an S3-compatible endpoint such as MinIO
- non-default `WHATSAPP_VERIFY_TOKEN`
- `WHATSAPP_APP_SECRET`
- `WHATSAPP_ACCESS_TOKEN`
- `WHATSAPP_PHONE_NUMBER_ID`
- `SMART_ESGP_WHATSAPP_CLAIM_TTL_SECONDS` between 30 and 3600 seconds
- auditor-level token for manual outbound sends

Production readiness rejects placeholder secret values such as `change-me-*`, `replace-with-*`, and `placeholder`.
